## 一个重复劳动引发的念头

做 LLM 评测的人都有个体会：跑一轮 bench 试标，agent 要跑几十个 turn，人得全程盯轨迹——工具调用对不对、卡在哪一步、判分器为什么扣分。一轮下来半小时起步，而这样的轮次一天要跑好几轮。

盯到第三轮的时候我开始想：**读轨迹、查判分点这种活，本身就是个能被 Agent 干的事**。

于是有了这个项目：[my-eval-agent](https://github.com/shuangluo1206/my-eval-agent)——一个垂直于评测场景的 Coding Agent，一句话定位是「**评估 Agent 的 Agent**」。

## 为什么不用框架

市面上现成的 Agent 框架很多，但我选择从零手写 Agent 循环，原因有三：

1. **简历项目的价值在细节**：SSE 流式拆包时同一个 chunk 可能同时带 content 和 tool_calls 增量、工具参数要从字节流里一片片拼出来、parse 失败怎么兜底——这些坑只有自己踩过才有面试话术
2. **垂直工具需要干净的挂载点**：评测场景的行为定制（轨迹瘦身、前置校验、达标收尾）都挂在循环钩子上，用框架反而要绕
3. 体积：核心三层加起来不到两千行，可控

## 架构：三层各司其职

```
cli → agent/loop → ai（Model 接口）+ tools（ToolRegistry）
```

- **AI 层**：抹平模型差异。`ToolCall` / `LLMMessage` / `LLMEvent` 三个类型契约是全系统的枢纽，OpenAI 兼容层一套方言适配多家模型
- **Agent 层**：手写 `while` 主循环——LLM 事件流 → 拼装工具调用 → 执行 → 结果入历史 → 下一轮，直到模型不再要工具
- **工具层**：全部换血为评测工具。MVP 两个：`run_eval`（跑一轮试标）和 `read_trials`（读轨迹），后续加 `diff_gt`（比对 groundtruth）

## 造它顺便学会了什么

为了不瞎写，我先精读了一个开源教学 Agent 的源码（[my-easy-pi](https://github.com/KNeegcyao/my-easy-pi)，10 章渐进式教程），最大的三个收获：

1. **`ToolCall` 是模型到代码世界的唯一动作通道**——它串起了事件生产、循环拼装、工具分发、消息记账、请求回传五处
2. **循环骨架各家一模一样，垂直化差异全在钩子+工具层**——这是整个项目最值钱的一句话
3. **工具崩了不等于循环崩了**——异常转成 isError 的 toolResult 喂回模型，它能看到并换姿势重试
