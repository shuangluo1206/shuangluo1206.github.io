## 问题的来源：跑 bench 跑出来的「模型脾气」

做评测的人对模型的毛病有一种朴素的熟悉感——不是从论文里读来的，是被坑出来的。我在 bench 实测里踩到的两个：

1. **主力模型偶尔在网关处开局就报错**（502/超时，一个字还没吐）——大概率是抖动，重试往往就好
2. **主力模型的 write_file 有老毛病：参数里丢 path**——不是偶发，是稳定复现的脾气

第二个特别有意思：模型很努力地调工具，参数碎片拼出来一看，`{"content":"周均负载 32,244 MW"}`——就是没有 path。文件写哪？不知道。

如果只跑一个模型，这些坑只能人肉盯。但既然手上有一个 OpenAI 兼容的聚合网关、一个 key 能调多个模型，那很自然的想法是：**让另一个模型当备胎**。

## 设计：一个「插座转接头」

我的 Agent 循环只认一个 `Model` 接口。所以路由器不是「调度器」那样的旁路系统，而是——

```
class ModelRouter implements Model { ... }
```

它自己实现 `Model` 接口，里面站着两个真模型（主力 + 备用）。Agent 拔插的还是同一个插座，**根本不知道背后站着两个模型**。这是整个设计里我最满意的一点：路由是零侵入的，循环一行没改。

## 三种失败，三种策略

实现过程中发现「模型失败」其实是个混合词，得拆开对待：

### ① 开局报错 → 当轮无缝切换

主力一上来就吐 error 事件（一个字还没说），这时历史里什么都还没发生。路由器把错误事件**吞掉**，本轮直接改用备用模型跑完。关键判断：**这不算降级**——可能只是偶发抖动，下一轮主力还有机会。

### ② 质量缺陷 → 连败计数，永久降级

write_file 丢 path 这种「稳定脾气」就不是抖动能解释的了。路由器在事件流旁边开个小缓冲，监视工具参数拼装：`done` 事件时如果 JSON 里没有 path 字段，连败计数 +1，达到阈值（我设的是 1，一票否决）就永久降级到备用。

这里有个微妙的设计取舍：**事件已经放行了，没法收回**。所以流中途发现的缺陷只能记账，下一轮才生效——本轮该失败的 write_file 还是会失败。可以接受，因为循环本身有兜底（工具失败会转成 isError 结果，模型能看到并重试）。

### ③ 流中途报错 → 只计数，下轮生效

事件已经放行没法收回，和 ② 同理。

## 验收：一条 prompt 走完两套路由

测试用两个 fake 模型按剧本演（不烧 token），一条 prompt 把「无缝切换」和「质量降级」全触发一遍。跑出来的路由决策日志：

```
· 主力 GLM-5.3 开局报错（网关 502）→ 当轮无缝切 DeepSeek-V4-Pro（下轮主力继续）
· 主力 write_file 丢 path（bench 实测老毛病），连败 1
· 主力连败 1 轮（阈值 1）→ 永久降级到 DeepSeek-V4-Pro
```

三个断言全过：

- 主力的报错**从没漏到 Agent**（消息历史里没有 `[模型错误]` 字样）
- 丢 path 的 write_file **真的失败了**（isError 结果入历史）
- 任务**无损完成**（报告和摘要两份文件都落盘）

## 一点感想

这个功能做完回头看，最有价值的不是「双模型」本身，而是**被迫把「模型失败」分类**的过程：环境抖动和模型缺陷是两种病，治疗方案完全不同——前者宽容（当轮换人，下轮还你机会），后者果断（一次实锤就永久换人）。

评测工程师的日常不就是干这个的吗？给失败分类、定触发条件、决定干预力度。只不过这次的对象，是我自己的 Agent。
